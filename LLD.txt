In system design, the focus is on architecture. 
In LLD, the focus is on implementation.
  the discussion is about methods, relationships, data models and state transitions.
  we are expected to write class definitions, method signatures and bit of a logic.
  design patterns are important - you should be able to tell why strategy design pattern is used vs factory design pattern.
  Establish the scope before you start designing.

------
Framework: 

R: Requirements
E: Entities
C: Class Design
I: Implementation
E: Extensibility

1. Requirements
  Primary capabilities: what operation must this system support?
  Rules and Completion: what conditions define success, failure, or when the system stops or transitions state? 
  Error handling: how should system respond when the inputs or actions are invalid? 
  Scope boundaries: what areas are in scope and what areas are explictly out?

2. Entities and Relationships
  Identify the entities
  Then, think through how they interact to get relationships.

3. Class Design
  Go through entity-by-entity, top-down (Eg: In Tic Tac Toe game, 
Start with the Orchestrator - Game, then the supporting entities like Board, Player etc.)
  For each entity, answer two questions - State (objects) and Behaviour (methods). 

4. Implementation
  Start with happy path, and then move to Edge cases (invalid inputs, illegal operations, out of range values etc.)

5. Extensibility

Design Principles: 
  Design principles guide decision making to write a clean, extensible and maintainable code.

  we have to consider two types of principles.
  1. general software design principles
  2. object oriented design principles

general software design principles: 
  1. KISS: Keep it simple, stupid: If it works, leave it. Do not over-engineer at the beginning itself. 
  2. DRY: Don't repeat yourself. If same code is at multiple places, refactor them to create a shared method.
  3. YAGNI: You aren't gonna need it.
      Build what you need now, not what you might need later.
      It doesn't mean "never think ahead". It means "don't build ahead".
      Design with extension in mind, but only implement what is needed now.
  4. Separation of Concerns
      Different parts of code should handle different responsibilities, and they shouldn't know about each others internals.
  5. Law of Demeter

Object oriented design principles:
  1. SOLID principles
      S: Single Responsibility Principle
          A class should have one reason to change. If a class mixes multiple concerns, split them.

Bad: 
class Report {
  void generateContent() { // add impl }
  void printToPDF() { // add impl }
  void saveToFile() { // add impl }
}

Good: 
class Report {
  void generateContent() { // add impl }
}

class PDFPrinter {
  void print(Report report) { // add impl }
}

class FileStorage {
  void save(Report report) { // add impl }
}


      O: Open/Closed Principle  
          Classes should be open for extension but closed for modification.
            You should be able to add new behaviour without changing existing code.
            This usually means using Interfaces and Abstract classes so we can add new implementation without touching the original code.

Bad: 
class PaymentProcessor {
  void process(String type, double amount) {
    if (type.equals("credit")) {
      // add impl
    } else if (type.equals("paypal")) {
      // add impl
    } 
  }
}

Good: 

interface PaymentMethod {
  void process(double amount);
}

class CreditCardPayment implements PaymentMethod {
  public void process(double amount) {
    // add impl
  }
}

class PaypalPaymentMethod implements PaymentMethod {
  public void process(double amount) {
    // add impl
  }
}


      L: Liskov Substitution Principle
          The Subclass can add new behaviour but it can't remove or break behaviour that the parent promised.

Bad: 

class Bird{
  void fly() {
    // impl
  }
}

class Penguin extends Bird {
  public void fly() {
    throw new UnsupportedOperationException("Penguins can't fly");
  }
}

Good: 

interface Bird {
  void eat();
}

interface FlyingBird extends Bird{
  void fly();
}

class Parrot implements FlyingBird{
  public void eat() {
    // impl
  }
  public void fly() {
    // impl
  }
}

class Penguin extends Bird{
  public void eat() {
    // impl
  }
}
      I: Interface Segregation Principle
          Prefer small, focused Interfaces over large, general-purpose ones.
            So if a class only needs two methods from an Interface with ten methods, then that Interface is big

Bad: 

interface Worker{
  void work();
  void sleep();
  voi eat();
}

class Robot implements Worker{
  public void work() { // add impl}
  public void sleep() { // Robots don't sleep }
  public void eat() { // Robots don't eat }
}

Good: 

interface Workable {
  void work();
}

interface Restable {
  void sleep();
}

interface Feedable {
  void eat();
}

class Human implements Workable, Restable, Feedable {
  public void work() { // add impl }
  public void sleep() { // add impl }
  public void eat() { // add impl }
}

class Robot implements Workable { 
  public void work() { // add impl }
}

      D: Dependency Inversion Principle
          Depend on abstractions, not concrete classes - and inject the dependency instead of creating it inside. So OrderService takes a Notifier interface, and I can swap email for SMS, or a fake for testing, without
          changing it.
          
OOPS concepts: These are the mechanisms that programming language gives to actually implement the clean code.

Encapsulation: 
  Its about binding data and methods into a single unit - a class and hiding internal state so it can't be accessed directly.
  Access modifiers like public, private and protected control visibility and we can expose controlled access through methods that can enforce rules.

  For example, take a BankAccount class where we keep balance variable private and it only lets us change the balance through deposit() and withdraw() methods.

Abstraction:
 Its about exposing what an Object does and hiding how it does it.

 For example, a PaymentMethod Interface exposes process() method, the caller doesn't care whether its payment through Credit card or Paypal underneath.
  OrderService doesn't care which PaymentMethod implementation it gets.

  Difference b/w Encapsulation and Abstraction: 
    Encapsulation: it is about protecting the data.
    Abstraction: it is about exposing only the essential behaviour
  
    Encapsulation and Abstraction are related. Encapsulation is one of the ways to achieve Abstraction. Encapsulation is the mechanism and Abstraction is the design goal.

Polymorphism:
  It allows a single Interface or method to take multiple forms, so the same call behaves different depending on the actual object involved.
  There are two types: Run-time polymorphism (method overriding) and Compile time polymorphism (method overloading)
