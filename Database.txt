ACID principles - Those are guarantees from a database. They are not related to SQL.

Atomicity: 
  Its about all or nothing execution. Either both operations succeed or neither does.
  Important principle in ACID.
  Eg: Bank transfer, order placement etc. 
  
  Eg: 
  BEGIN; 
  UPDATE ACCOUNTS SET BALANCE = BALANCE - 100 WHERE ID = 'A';
  UPDATE ACCOUNTS SET BALANCE = BALANCE + 100 WHERE ID = 'B';
  COMMIT;
  
  Both of the above operations execute as a single piece of work.
  If any statement fails, the database rolls back the entire transaction, preventing partial state changes.

Distributed Atomicity:
  Why Atomicity is hard in distributed systems (due to partial failures).
  It can be achieved using: 
  Two phase commit 
  Three phase commit 
  Saga pattern
  Outbox pattern
Tradeoffs between Atomicity and Availability.



Idempotency and Compensation; 
  When strict Atomicity is not possible (Eg: In Microservices), system rely on
  1. Idempotent operations (retries don't change outcome)
  2. Compensating transactions (reverse a failed step)
  3. Event-driven design (using queues to ensure eventual consistency)

Eg: In Microservices, 
Step 1: Deduct Payment
Step 2: Reserve Inventory
Step 3: Create Order.
If Step 3 fails, trigger compensation = refund payment + release inventory.

Database Normalization: 
  It is used in Relational Database systems to organize tables to reduce Data Redundancy and improve Data Integrity.
  It involes applying a set of rules known as Normal Forms. 
  Primary goals of Database Normalization are: 
  1. Eliminate Redundancy: Storing same piece of data multiple times can waste storage and cause storage inconsistencies.
  2. Improve query performance.

INNER JOIN: Show me the rows where there is a match in BOTH THE TABLES.
LEFT JOIN: Show me everyone from the LEFT table and the overlapping data. If a Customer has an Order, show it. If they don't, just leave the Order NULL. This is the most common join.
RIGHT JOIN: Show me everything from the RIGHT table and the overlapping data. If we know who ordered it, show their name. If we don't know the Customer, leave their name NULL. 


If we simply joined Users and Downloads, we would get a long list of rows:
• Alice | Instagram
• Alice | YouTube
• Bob | WhatsApp


SELECT Users.Name, COUNT(Downloads.App_Name) AS Total_Downloads
FROM Users
LEFT JOIN Downloads ON Users.User_ID = Downloads.User_ID
GROUP BY Users.Name;


In an interview, they might ask you: "What happens if Charlie has zero downloads? Does he show up with a 0 or a 1?"
This depends on what you count:
• COUNT(*): This counts the row. Since Charlie exists as a row in your LEFT JOIN (Charlie | NULL), SQL will count that row as 1. (Wrong result!)
• COUNT(App_Name): This counts actual data. Since the App_Name for Charlie is NULL, SQL ignores it and gives you 0. (Correct result!)

Rule of Thumb: When counting after a LEFT JOIN, always count a column from the Right Table to ensure you get a 0 for users with no activity
